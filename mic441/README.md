# ESP32-S3 + 双 INMP441 立体声采集（WiFi 网页实时拉流）

> 板子：ESP32-S3-N16R8（MicroPython 1.22.1，MAC `24:ec:4a:3c:84:e0`）
> 现状（2026-11-01 18:05，**已收工**）：16 kHz / 双麦立体声 / WiFi 网页，全链路打通并实测。
> **采样率只用 16 kHz，32K 和 48K 实测有问题，已放弃**（见下方"采样率支持状态"）。
> 两颗麦并联在 SD=9 / SCK=10 / WS=11，L/R 分左右（**3V3=左，GND=右**，实测与手册相反）；
> 程序开机自动实测每路能量，接反了立刻能看出来；
> 录到的人声峰值 7996（−12.3 dBFS），频谱有清晰共振峰。

## 一、先说结论：为什么走 WiFi，不走串口

| 通道 | 实测带宽 | **16kHz/16bit 立体声 64 KB/s** |
|---|---|---|
| 串口 115200 | 11.5 KB/s | ✗ 差 3 倍 |
| **本板 WiFi 上行** | **429 KB/s**（4 MB / 9.55 s，实测） | ✓ 余量 13 倍 |

所以"串口太慢"的判断是对的，WiFi 网页拉流是合适的路子。而且不必用 WebSocket：
普通 HTTP + chunked 就够，板端不用做握手，浏览器用 `fetch` 的流接口直接读 PCM。

## 二、接线（双 INMP441 → 板子）

两颗麦的 **SD / SCK / WS 全部并联**，靠 **L/R** 分左右：

| INMP441 | 接到 | 说明 |
|---|---|---|
| VDD | 3V3 | **别接 5V** |
| GND | GND | |
| SCK | **GPIO10** | 两颗并联 |
| WS | **GPIO11** | 两颗并联（WS 频率 = 采样率，现在 **16 kHz**） |
| SD | **GPIO9** | 两颗并联 |
| L/R | 见下表 | 一颗接 3V3、一颗接 GND |

### 左右声道约定（2026-11-01 实测确定，**与手册相反**）

| 麦 | L/R | 落在 | 装在哪 |
|---|---|---|---|
| 左麦 | **3V3** | 左声道（ch 0） | **物理左边** |
| 右麦 | **GND** | 右声道（ch 1） | **物理右边** |

手册和网上通说"L/R 接 GND = 左声道"，**在这套板子上不成立**。
证据：只留 GND 那颗时左声道 100% 全是 0；插上 3V3 那颗后左声道立刻有能量，
且两路样本只有 4% 相同、互相关 0.497（是两条独立通道，不是抢同一根线）。
所以：**按实测定方向，不要按手册推**。代码里的映射已经和上表一致，不需要改。

### 两颗麦间距：建议 6 cm（5~7 cm 都行）

**一个样本对应的路程差 = 343 m/s ÷ 采样率**。16 kHz 下是 **21.4 mm**。不同间距：

| 间距 | 最大时延（16k） | 空间混叠边界 |
|---|---|---|
| 4 cm | 1.9 样本 | 4.3 kHz |
| **6 cm** | **2.8 样本** | **2.9 kHz** |
| 8 cm | 3.7 样本 | 2.1 kHz |
| 10 cm | 4.7 样本 | 1.7 kHz |

（混叠边界只由间距和声速决定，跟采样率无关；采样率只决定时延能细化到什么程度。）

人声主能量 300~3400 Hz，8 cm 时 2.1 kHz 以上就开始分不清左右；6 cm 两头都不亏。
另外要求：**同朝向、同轴、中间别挡东西**，线尽量等长。

> 这三个脚沿用你旧 441 项目的接法（`SD=9 SCK=10 WS=11`），零改动。
> 注意：10/11/12 是将来 80MHz 彩屏的 IOMUX 脚；彩屏一直暂缓，麦克风先用。
> 真要错开，就改成 `SCK=15 WS=16 SD=14`（只需改 `micapp.py` 顶部三行）。

**L/R 不用纠结**：程序用 STEREO 收两路，开机实测哪一路有能量就用哪一路
（`detect()`）。历史笔记里"GND=左 / 3V3=右"与数据手册口径不一致，所以这里不靠笔记、靠实测。

页面上：
- **▶ 实时监听**：连续播放，上方波形（蓝 = 左声道，绿 = 右声道，**dB 刻度**）、左右电平条、实际速率、声像
  - 波形必须用 dB 刻度而不是线性：线性下正常说话只有 1~2 个像素高，肉眼等于没有（这是踩过的坑）

跟不上的一方只丢它自己，不会拖累别人，也不会拖累采集。

**改了 `mic.html` 必须重启板子**（页面是开机时缓存进内存的，改完不生效会让人以为改错了）：
按一下板子 EN 键，或者串口里 Ctrl-D。

## 四、客观核验（不看耳朵）

```bash
python3 mic_check.py --sec 5              # 抓 5 秒实时流并分析，存 mic_check.wav
python3 mic_check.py --sec 5 --rec        # 改用 /rec.wav，完整文件最稳
```

判据（双麦时还会打印两路互相关、亚样本时延、声源方向）：

| 指标 | 正常范围 | 异常含义 |
|---|---|---|
| 有效速率 | 16000 ±5% | 丢帧 / 带宽被别的页面占了 |
| 峰值 | 说话 3000~20000 | <100 = 没接麦或接线错 |
| RMS | 静音几十，说话上千 | 恒 0 = 无声；恒满 = 爆音 |
| DC 偏置 | \|mean\| < 50 | 偏大 = 位对齐错 |
| >5kHz 能量占比 | 人声 < 30% | 30%+ = 多半是噪音/错位 |
| 谱平坦度 | 人声 < 0.3 | ≈1.0 = 白噪音 |

## 五、和旧 441 做法差在哪（旧方案为什么"不牢靠"）

| 旧做法 | 问题 | 现在 |
|---|---|---|
| `format=I2S.STEREO` 但只接一只麦，靠猜 L/R | L/R 接反就整串 0，且笔记说法与手册相反 | 两路都收 + 开机实测选声道 |
| 每帧用 Python 逐字节移位解析 | 慢，且容易"靠试"出结论 | `viper` 一行 `>>16`，0.21µs/样本 |
| `buf[i]` 循环 + `print` 到串口 | 串口比音频慢得多，必然阻塞 | 只走网络，串口只打状态 |
| 录音循环里刷 OLED | 阻塞 → I2S DMA 溢出 → 爆音 | 采集与显示彻底分开（浏览器画图） |
| 改 WAV 头来"校正"采样率 | 只改了播放速度，没验证真实采样率 | 用到达时间斜率测速率，误差 −0.2% |

## 九、8 颗麦能不能做 Boomerang 那种枪声定位？——**不能，卡点在硬件不在代码**

结论先给：**这套东西能做到"强脉冲的粗略方位"，做不到"狙击手定位"**。四条独立的硬限制：

### 1. 通道数就先卡死（A 级，本地 IDF 源码）

```
components/soc/esp32s3/include/soc/soc_caps.h:  #define SOC_I2S_NUM (2U)
```

ESP32-S3 只有 **2 个 I2S 控制器**；INMP441 是标准 I2S 从设备，**只能靠 L/R 脚二选一**（它不支持 TDM），
所以一条总线最多 2 只 → **整颗 S3 最多 4 只麦**。8 只接不上。
想突破只有两条路，都不好用：换 TDM 麦（INMP441 不行），或者用第二块板——
但两块板的时钟不同步，跨板 TDOA 直接废掉（这正是 Boomerang 用硬阵列的原因）。

### 2. 时间分辨率差一到两个数量级（算术，A 级）

| 采样率 | 1 个样本对应的路程差 |
|---|---|
| 16 kHz（现在） | **2.14 cm** |
| 48 kHz | 7.1 mm |
| 192 kHz | 1.8 mm |

6 cm 基线上最大时延只有 2.8 个样本，角度量化 ±10~15°，做亚样本插值能到 ±5° 左右。
枪声定位要的是 **±1° 量级**，还要求几微秒的时间精度。

### 3. 带宽根本不够看激波（A 级 + 公开资料）

Boomerang 之所以能算"脱靶距离"，靠的是超音速弹丸的**弹道激波（N 波）**：正压—负压一个完整周期
大约 0.1~1 ms，要把它记录成波形，带宽要 **20~50 kHz**。现在 16 kHz 采样只有 8 kHz 带宽，
激波会退化成一个"咔"的脉冲——**只能知道"有响"，测不出脱靶距离**。

### 4. 阵列机械公差（B 级）

Boomerang 是车载硬阵列，基线几十厘米到米级，几何尺寸要精确到毫米、还不能振。
面包板 + 杜邦线搭的阵列本身就在抖，基线一抖，TDOA 全是噪声。

### 那 8 只麦还能干点什么

- **4 只 + 双 I2S 总线 + 48 kHz**：做一个**二维粗方位**（拍手、敲击、口哨这种强脉冲），
  刚性铝型材搭阵列，精度大概 ±10°，是"能玩且能出结果"的上限。
- 另外 4 只：留作备份/替换，或挪去别的项目。
- 真想碰"声音定位"这个题目，正路是**专用阵列板（多通道同步采样 ADC + FPGA/CPLD）**，
  或者直接用成品声学传感器——不是靠加麦的数量堆出来的。

> 一句话：**Boomerang 难的从来不是"麦多"，是"通道同步 + 高采样 + 宽频带 + 刚性基线"四件事同时成立。**
> 这套板子在前两件上就已经到顶了。

## 十一、采样率支持状态（2026-11-01 收工时的最终结论）

| 采样率 | 状态 | 实测情况 |
|---|---|---|
| **16 kHz** | ✅ **唯一正常** | 单连接 9.92 秒音频 / 10.04 秒，0% 满量程；Mac 和 iPhone 上都能正常听 |
| 32 kHz | ❌ 有问题 | 数据链路单连接能跑满（8.000s / 8.02s），但实际听感不对；iPhone 戴耳机同样不行 |
| 48 kHz | ❌ 有问题 | 单连接 10.000s / 10.05s 能跑满，但实际听感不对；两个客户端就顶到上行上限开始丢帧 |

### 32K / 48K 到底是哪里不对——**没有定论，如实记录**

- **确认过的**：在 Mac 上开音箱时会啸叫（正反馈）。证据：播放时流里是满量程 0 dB，停掉播放后立刻只有峰值 241。
- **但对不上的**：用户用 **iPhone 15 + 耳机** 试 32K/48K **也不行**。戴耳机没有音箱回路，所以**啸叫解释不了这一条**。
- **没分离出来的**：带宽/丢帧、iPhone Safari 对 16k 以上 PCM 流的处理、播放端缓冲区采样率，
  这三者哪一个是主因，**没有逐一验证**，不做猜测。
- **唯一可靠的判据**：现在这一档（16 kHz）在 Mac 和 iPhone 上都正常，就停在这儿。

以后要重开这个题目，建议先做的**单一变量实验**：同一段录音分别用 16k / 32k 抓成 WAV（走 `/rec.wav`，
绕开浏览器），先在 Mac 上用播放器对比听——先排除浏览器，再谈设备。
